## 2. 目标、需求追踪与明确非目标

### 2.1 目标

恢复读写、缓存、视图生命周期、编译及历史的有限资源属性，同时保留已经验收的编辑速度、显示效果、选择行为、音乐语义和文件兼容性。

“有限内存”不等于“任意工程、任意历史长度，整个进程永远只用同一个常数”。必须分别说明：

- 常量预算的工作页、缓存、在途任务和解码缓冲；
- 随 Track / Segment / 页目录等必要元数据增长的部分；
- 可共享的不可变内容、冷索引及 owned spill；
- History / Clipboard 的实际所有权和尚未批准的总磁盘策略；
- WPF / CLR / native / 用户 SoundFont 等不属于同一个预算的资源。

不以把无界 RAM 转移成无记录、无清理的无界磁盘使用作为“完成”。

### 2.2 简短 requirement trace

| 项目 | 本次约束 |
| --- | --- |
| 输入 | 冻结 Project revision、不可变分页源及 overlay、正式 Selection、History / Clipboard、活动 Workspace 和 consumer |
| 正式输出 | 原有编辑结果、选择结果、诊断、canonical、导出与 `.midora` 语义不变；允许改变内部布局、所有权、缓存和准备步骤 |
| 范围与边界 | `[start, end)`、隐藏内容、端点顺序、同 tick 碰撞、Root / Usage 生命周期及 source trace 不变 |
| 原子性 | 取消、I/O 失败、预算不足、旧 revision 或校验失败不得发布部分编辑，不得破坏旧项目文件 |
| 诊断 | 保留严格失败与损坏隔离；新增性能计数属于诊断，不以静默重试或屏蔽错误掩盖问题 |
| 持久化 | 默认不改 Project Format 3 writer、Format 1/2 reader、冻结 wire / golden 或 presentation 语义 |
| 运行时 | 索引、lease、缓存、临时页、任务与订阅必须有 owner、计账、失效规则和释放时机 |

### 2.3 禁止作为默认修法的措施

- 删除严格验证、保存自校验、重复 ID 检测或来源校验。
- 静默清空 / 截短 Undo，删除音乐对象，减少正式事件，改变同 tick 规则。
- 降低现有概览或钢琴卷帘精度，隐藏大选择预览，恢复全局瓦片失效或 UI 同步扫描。
- 在正常编辑 / 关闭流程频繁主动 GC，或以压低 Working Set 数字代替修复持有链。
- 重引入自动快照 / 崩溃恢复、后台自动保存或新的产品功能。
- 因为曾有开发期破坏兼容的授权，就默认为本轮允许破坏现在已冻结的格式。
- 把主进程预算误称为包含任意 SF2 / SFZ、Worker、GPU 和整个系统的总内存保证。

确需改变文件格式、正式行为、历史保留策略或合法任务的拒绝边界，先提交证据、受影响条款和候选方案，请用户决定；不能以优化任务为由静默实施。

## 4. 时间性能、内存与正确性的共同门槛

### 4.1 时间取舍不预先写成“允许整体慢 X%”

| 路径 | 工程预期，尚非实测承诺 | 重点防止的代价 |
| --- | --- | --- |
| 只读访问、重复转换、关闭泄漏 | 大概率持平或更快，减少分配和 GC | 为省表而把每次 ID 查询改成全源扫描 |
| 常用拖动、缩放、选择、近期 Undo | 不预先接受可感知退化 | 缩小热缓存、UI 等待冷页、错误全局失效 |
| 冷范围 / 被淘汰计划重建 | 可能增加后台准备时间 | 多次访问相同工作集仍反复淘汰、恢复状态成本失控 |
| Opaque 大 payload、冷索引、深层 Undo | 可能增加解码或 I/O | 逐记录读写、重复解压、随机磁盘访问放大 |
| 严格流式保存 / 打开 | 额外计长 / 多遍扫描可能与减少对象转换相抵 | 用不等价验证工作量伪造提升 |
| 大 Logical 展开、外部排序 | 可能是时间代价最大的部分 | spill / 多轮归并、跨阶段重复排序和释放过早 |

判定规则：

- **10% 是强制调查阈值，不是允许退化额度。** 可重复且超过测量噪声的退化即使不足 10% 也列出；达到 / 超过 10% 必须归因、比较替代方案，再判断是否值得取舍。
- 新出现可感知的 UI 卡顿、首次访问异常长尾、错误旧图或长时间空白，不能被更好的平均值掩盖，属于阻塞项。
- 已有长任务多花几秒是否可接受，要结合绝对耗时、频率、取消能力和内存收益逐项决定，不能一概套用用户曾接受的 3～5 秒。
- 缓存 miss 应主要增加后台准备耗时，不能改变正式内容或把准备成本转嫁到 UI / 音频活动线程。
- 没有完成等工作量前后测量时，只写“预期 / 待测”；不能承诺整体降低到某个 GiB 或固定加速倍数。

### 4.2 内存计账及硬断言

每个大容器 / 缓存 / 任务记录 owner、独占字节、共享底层、容量而非仅 Count、峰值、失效键、释放条件及活动 lease。共享页只按实际物理所有权计一次，同时可单列各消费者引用数量。

必须区分 WS、Private Bytes、自然 GC 下托管占用、受控 post-GC live、累计分配、GC committed / fragmentation、页缓存、native / WPF 位图和 owned spill。不能把累计分配当成常驻，也不能要求退出项目后 WS 立即回到启动值。

阶段 1 冻结现有预算清单，后续填上新增预算的来源和理由。已确认的 64 MiB 解码 / 编辑预算、256 MiB 共享栅格缓存等，分别属于对应层，不可相加后宣称是进程总上限。活动 lease、双版本交接和任务工作缓冲必须独立计账，不能用“LRU 在上限内”掩盖旁路占用。

验收优先使用可解释的计数断言，例如“只读遍历不新增全量 facade 映射”“订阅数随有效消费者而非帧数增长”“冷 cache 达到字节平台”“关闭后不再保留旧 Project”。WS 阈值是辅助证据。

### 4.3 正确性硬门

- 小样本参考模型、正式 schema / golden 和明确 SRS 边界共同作为 oracle；当前实现若有已知错误，不能把其错误输出固化为新规范。
- 同输入重复、不同页边界 / 缓存命中 / 线程完成顺序下，正式输出、诊断、来源、ID 和排序一致。
- Full / Incremental 等价；从范围中途恢复状态、同 Root / Usage 跨轨道共享、Loop / Pre-Roll、硬边界和 NoteOff 行为不变。
- Note later-loses / Event later-wins 只作用于相关编辑键；导入的未命中重复记录和隐藏内容不被顺便清理。
- 成功一次 Undo；取消 / 失败零部分发布；Undo / Redo 恢复正确选择且不重新抽随机数或求表达式。
- Format 1/2 可读，Format 3 严格往返；保存自校验、原子替换、迁移副本和损坏隔离不削弱。

| Event / Parameter | 自由线、直线、Shift 固定值 / 固定 tick、逐点修改、Lane 切换、选择恢复 |
| 容器与定义 | Segment Split / 内容窗口、Track / Root / Usage 操作、Instrument / SubVoice / Mapping 编辑及引用变化 |
| 历史 | 首次新区域、原位置重复、跨区域、深层 Undo、Redo、新编辑丢弃 Redo 分支、Clipboard 替换 |
| 只读与消费 | Arrangement、三类钢琴卷帘及 Lanes、Conductor、对象列表、Onion、All Tracks、编译、播放 / 预览、MIDI / Audio 导出 |
| 生命周期 | 新建 / 打开 / 保存 / Save Copy / 关闭、迁移、失败清理、Tab 隐藏 / 关闭、Project 切换 |

这里只定义覆盖索引，不重新解释工具的适用对象或原有行为。对不适用组合记录“不适用及依据”，不为补测试矩阵新增产品能力。

### 5.3 端到端计时

同一动作记录至少以下事件点：

1. 输入被接受 / 菜单命令开始。
2. 选择解析与冻结完成。
3. detached 规划、碰撞归并和校验完成。
4. root swap / 正式提交完成。
5. Selection / 属性 / 失效通知处理完成，UI 可继续输入。
6. 首批正确内容可见，随后当前 viewport 不再包含过期内容。
7. 所需后台编译完成，消费结果变为 current。

后台编译和栅格刷新可能并行，不能简单累加重叠阶段；分别报告总墙钟、UI 可操作延迟、可视内容收敛和编译就绪。取消也测“点击 Cancel→观察到取消→任务退出→资源归还”，不是只测 token 设置耗时。

“命令本身很快”“Undo root swap 很快”不能替代 1～7 的链路数据。

### 5.4 冷热、重复次数和探针干扰

- 分开测：新进程首次；同会话新区域；同区域重复；预算压力后被淘汰区域重访。新进程不等于 OS 磁盘缓存也冷，必须如实标注，不清理系统缓存来伪造对照。
- Release / x64、同机器、同 runtime、同音频及后台编译配置；前后版本交替运行。自然产品配置和关闭 / 延迟编译的归因探针分别报告，不混用。
- 大流程默认 3～5 次，报告中位数、最小 / 最大和样本数；如成本过高减少次数，说明原因和置信局限。只有帧 / 查询样本足够多时才报告 p95 / p99，不从三次运行推导可靠长尾分位数。
- 自然运行计时与强制 GC 归因分开。WeakReference 测试在调用栈退出、后台任务和 Dispatcher 工作收敛后进行，防止诊断局部变量造成假泄漏。
- 实际 WPF STA / 主题 / Controller / Surface / 命令路由和失效通知必须纳入自动测试；离屏 WPF 不等于用户已确认视觉体验，也不需要调用 computer-use。
- 帧采样、内存采样与内部计数必须低开销 / 可关闭；重型 heap / 分配分析单独运行。诊断不进入 Project、Undo、Modified 或音频活动线程。
- 大样本串行执行，测试有超时、取消、磁盘余量和进程资源保护。基线已知超预算时记录“受保护中止”，不强求 OOM 或整机失去响应来完成曲线。

### 5.5 产物和路径

小型可重复 fixture、测试源码、摘要报告可以按仓库约定追踪。大型 MIDI / `.midora`、CSV、heap dump 和临时内容不进入 Git；生成在受控测试输出 / owned 临时目录，记录其路径及保留期限。

产品新增临时数据遵守 ProgramRoot 和现有 owner / lease 契约；正常保存事务仍服从同卷目标旁临时包的既有规则，不能为了统一 `.tmp` 路径而破坏原子替换。不要清理用户原文件、未知目录、活动 run 或旧 `%LOCALAPPDATA%\Midora`。

## 8. 阶段 3：遗漏的字节预算和活动租约

**对应：M06、M07、M09、M10。依赖：验收 A 通过。**

### 8.1 实施内容

1. 范围 canonical / realtime / sample plan 采用字节计账、复用和淘汰；活动 plan 有 lease，淘汰不能释放正在播放、准备或离线消费的内容。
2. 优先共享不可变底层，分别计算共享和独占内存。新增预算值先通过工作集测试记录在 ADR，不能以每个缓存都有限为由忽略多缓存及活动 plan 总和。
3. Opaque 页、ID cache、选择读取和 Clipboard 按 payload 实际字节计账；条数限制与字节限制并存，不复制或永久钉住每个大 payload。
4. PageBuilder 的 active / incomplete / pending 状态和数组实际容量统一计账；小尾页按需增长或 spool，输出仍按冻结的 Segment / kind / page 顺序。
5. 稀疏 Stable ID 去重使用自适应表示和有界外排等手段；仍检测全包跨文件重复，不重编号、不漏检。
6. 预算不足优先淘汰可重建内容、受控 spill 和后台容量调度。活动租约、单条合法大对象和多个 reader 的准入必须有明确规则，不在音频活动线程等待或分配。

### 8.2 自动验证

- F08：1,000 个范围 / 配置组合，达到预算平台；超工作集重访、活动计划替换、取消 / Dispose / Project 关闭不出现错误释放。
- Seek 状态恢复、跨 Track 同 Root、Auto Root、共享 Usage、Buffering 中 Mute / Solo、Start / Stop / Reset；触及音频路径时运行对应零分配及回归测试。
- F05：MiB 级合法 Opaque 在查询、选择、复制、属性读取、保存、取消中均计 payload；未解释消息与 privileged Channel Mode SysEx 语义不变。
- F06：1 / 100 / 1,000 个小 Segment，全部 builder 状态预算受控；与冻结输出字节 / 顺序一致。
- 密集 / 稀疏 / 极大 ID、跨文件重复、异常 extent、溢出、spill 失败；安全失败且不改来源。

### 8.3 出口与交付

- 四类预算都有可执行计数断言及 owner；不能只报条目数量或配置上限。
- 按相同范围冷热对比准备耗时；新增 cache miss 代价独立列出，既有播放正确性不退化。
- 如要新增会拒绝原合法任务的硬限制，先停下该分支请求决策；不能把这种限制悄悄算作缓存实现细节。
- 交付计账 / lease ADR、资源平台与淘汰性能结果。人工结果并入验收 B。

## 9. 阶段 4：Logical / SubVoice 数据入口及流式持久化

**对应：M08、M11。依赖：阶段 3 工程门通过。**

### 9.1 实施内容

1. 先去掉 V2→V1 bytes→Parse 往返、成功路径的逐字段诊断字符串、两套全量 MemoryFiles 等不必要中间表示。
2. 对 Logical / SubVoice / Conductor 的大序列制定严格流式 writer / reader；length-delimited 采用有界计长 / 两遍或 owned spool，保留原 wire 和验证语义。
3. Reader 逐页建立 detached immutable source，完整验证后 adopt；避免完整 DTO→AddRange→ToArray 再复制整份内容。
4. 补齐仍走普通对象 / AddRange 的创建、恢复和长期小编辑累积路径，复用已有分页架构。**大批粘贴 / 生成的 Logical / SubVoice 已采用分页 root，不能误判为未优化而重写。**

6. Compiler 只读输入同步审计，避免 ordered facade / RawInstance 无意强留全对象；Logical 全展开预算留待阶段 5，不偷改其正式语义。

## 10. 阶段 5：编译展开与跨命令资源治理

**对应：M12、M13。依赖：验收 B 通过。此阶段复杂度最高，先测量再确定各内部改造深度。**

### 10.1 实施内容

1. 为 Logical 的 Trigger × SubVoice × Template Event × Loop / Mapping 建立展开压力梯度，分别测 Raw、canonical、来源、sort run、增量缓存及阶段交接的同时存活量。
2. 删除重复展开 / 拷贝和无意 facade 持有；对确有必要的大结果建立紧凑 value、分页 / 外排、可共享 canonical 和阶段释放方案。
3. 在正式排序、source trace、状态和范围边界确定后才允许释放上阶段资源。Full / Incremental、播放 / 导出都继续消费统一 canonical，不让各消费者重新编译一套语义。
4. History / Clipboard 按唯一底层内容与 lease 汇总 RAM、resident metadata、读缓存和 spill；冷元数据可外置，热 Undo 工作集可保留有界加速。
5. 丢弃 Redo 分支、替换 Clipboard、删除 / 关闭 Project 时，精确释放不再被引用的底层页；有效历史和新旧视图交接仍持有的页不能删除。
6. 保留全部有效 Undo 行为，Redo 不重新计算表达式 / 随机数。不得为了制造内存平台而自动裁剪历史。

### 10.2 特别边界

- 调查中的“每命令 64 MiB”不等于每一条 History 必占 64 MiB RAM；已发布编辑页已经落盘并使用共享读缓存。必须测独占字节，不把命令数乘预算当成事实。
- 有限 RAM、任意长历史和有限磁盘不能无条件同时保证。优先解决共享 / 冷元数据 / 所有权；若实际还需要 History 总磁盘硬限、拒绝新命令或裁剪历史，提交单独决策。
- 本阶段不可凭源代码上的一个 `ToArray()` 就全面替换编译器。先证明大样本的峰值持有关系，避免破坏已正确高效的 Pure MIDI 延迟 canonical 路径。
- 新编译布局与缓存只属于运行时。没有证据需要改 Project Format；若出现必要性，先走正式变更决定。

### 10.3 自动验证与出口

- 对原始和展开后的规模分别计数；比较合理常用规模和极端倍率，不仅测最坏情况。
- Loop（含 Gate 未超过 Template 但超过 Loop End）、Pre-Roll、逐音符隔离、映射、尾部、共享 Usage、同 tick、硬边界、稳定来源与资源分配全部通过。
- Full / Incremental / 不同并发与分页边界重复编译的形式和语义一致；不能只比较音符数量。
- 连续 Copy / Cut / Paste / Duplicate / 变换、深层 Undo / Redo、新分支、Clipboard 替换、保存后历史继续可用；取消 / spill 故障不破坏历史。
- 热 Undo、冷深层 Undo、大 Logical 编译的时间退化单列。新可感知卡顿或无法解释的周期性重建不作为必要取舍接受。
- 交付实测后的 M12 / M13 关闭依据，或明确未完成分支与决策请求；不能把“尚未测出”写成“已解决”。人工结果并入验收 C。

## 11. 阶段 6：全链路与最终收口

**对应：全部 M01～M13。依赖：阶段 5 工程门通过。**

### 11.1 连续场景

1. 导入 18M→选择 / 编辑→Undo / Redo→取消→切换 Lanes / Tab→Onion / All Tracks→保存→Save Copy→关闭→重开。
2. 新建 Logical 工程→复杂 Instrument / SubVoice→多种批量操作→增量编译→预览 / 播放→Seek→保存 / 重开。
3. 冷区域、热区域、驱逐后区域交替；跨越 Segment 右侧空白出现 / 消失临界点，检查以前已验收的卡顿与图像错误不复发。

## 13. 每阶段固定交付包

每阶段报告使用相同结构，避免用户必须从长日志中自行找结论：

1. **修改清单**：M 编号、模块 / 文件、根因、采用方案、用户可见变化；没有变化也明确说明。
2. **正确性结果**：运行命令、构建配置、通过 / 失败 / 跳过数量；重要测试名称和未运行原因。
3. **前后性能表**：相同样本、选择及冷热条件的时间、峰值 WS / Private、存活量、累计分配、I/O / spill；列出重复次数和原始证据。
4. **所有权断言**：三表、handler、completion、计划 / 页 / payload 字节、活动 lease、History / Clipboard / 临时文件等本阶段相关计数。
5. **风险与退化**：已知未解决项、测量盲区、新代价及接受 / 不接受依据，不能藏在“全部通过”后。
6. **人工操作卡**：仅在 A/B/C 提供正式定向清单；其他阶段说明将并入哪次验收。
7. **工作区与发布状态**：是否提交 / 推送 / 发布，严格按该次用户授权；不得以测试完成为由自动发布。

建议每条性能记录至少包括以下字段（可用机器可读结果和摘要表，不要求新建用户 UI）：

```text
build / source revision / dirty diff identity
fixture / source note count / compiled event count / selection / seed
operation / UI entry / cold-or-warm state / background-work configuration
selection-read / planning / commit / UI-ready / first-visible / current-visible / compile-ready
elapsed / sample count / median / worst
peak WS / peak Private / natural managed / controlled live / allocated bytes
cache owned bytes / leased bytes / spill bytes / read-write bytes / released-owner counts
correctness assertions / cancellation outcome / failures / evidence path
```

这些是诊断格式建议，具体机器可读 schema 在阶段 1 固定。原始结果、运行命令和简短复现步骤缺一不可；不把单次最优数据当成典型表现。
